# Pyright Strict Mode Policy for deep-worker-web

## 🚨 BINDING POLICY - NON-NEGOTIABLE

This document establishes the **MANDATORY** pyright strict mode policy for the deep-worker-web project.

## Policy Statement

**ALL Python code in the `app/` directory MUST pass pyright strict type checking.**

This requirement is:
- **Binding** - No exceptions
- **Enforced** - Via pre-commit hooks
- **Non-negotiable** - Cannot be weakened or bypassed

## Enforcement Mechanism

### Pre-commit Hook

The `.pre-commit-config.yaml` contains a mandatory pyright-strict hook that:
- Runs automatically before every commit
- Checks all Python files in `app/` directory
- **Blocks commits** if type errors are found
- **Cannot be bypassed** with `--no-verify`

### Configuration

Type checking rules are defined in `pyrightconfig.json`:
- `typeCheckingMode: "strict"` - Most rigorous type checking
- All type errors are reported as **errors** (not warnings)
- Unknown types are allowed (reportUnknownType: false) to avoid noise

## Prohibited Actions

❌ **DO NOT:**
- Remove or disable the pyright-strict pre-commit hook
- Weaken type checking rules in `pyrightconfig.json`
- Add Python files to exclude list
- Use `--no-verify` to bypass hooks
- Add `# type: ignore` comments without justification
- Create virtual environments (causes compatibility issues)

## Required Actions

✅ **DO:**
- Fix type errors in your code before committing
- Add proper type annotations to all functions
- Use typed imports from `typing` module
- Ask for help if stuck on type errors
- Test your code with: `python3 -m pyright app`

## Rationale

Type safety prevents runtime errors such as:
- Async/sync mismatches
- Attribute access on None values
- Incorrect function signatures
- Type incompatibilities

These bugs are caught at development time instead of runtime, saving debugging time and preventing production issues.

## Examples

### ❌ Bad (will fail type check):

```python
def process_data(data):  # Missing type annotations
    return data.value  # Could be None

async def get_result():
    result = sync_function()  # Wrong: treating sync as async
    return result.get()  # Could fail if result is coroutine
```

### ✅ Good (passes type check):

```python
from typing import Optional

def process_data(data: dict[str, str]) -> str:  # Proper annotations
    value = data.get("key")
    if value is None:
        raise ValueError("Missing key")
    return value

async def get_result() -> str:
    result = await async_function()  # Correct: awaiting async
    return result
```

This policy is established at project creation to ensure type safety from the start.
